Streaming (SSE) event flow

The exact event order, the delta types, and where the token counts hide.

Domain 2.3 · API Mechanics Domain 5.2 · Technical Fundamentals

Set stream: true and the response arrives as Server-Sent Events — a one-way HTTP stream from server to client (not WebSockets). The order is fixed:

event: message_start
data: {"type":"message_start","message":{... "content":[], "usage":{"input_tokens":11,"output_tokens":1}}}

event: content_block_start
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}

event: ping
data: {"type":"ping"}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Hello"}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":" there"}}

event: content_block_stop
data: {"type":"content_block_stop","index":0}

event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"end_turn"},"usage":{"output_tokens":6}}

event: message_stop
data: {"type":"message_stop"}
Event types
EventCarries
message_startThe Message with empty content and initial usage (input tokens; output_tokens = 1).
content_block_startA new block begins at index (text, tool_use, thinking, …).
content_block_deltaAn incremental piece for the block at index (see delta types).
content_block_stopThe block at index is complete. (Repeat the start→delta→stop cycle per block.)
message_deltaTop-level changes: stop_reason, stop_sequence, and cumulative usage.output_tokens.
message_stopThe stream is finished.
pingKeep-alive; may appear any number of times, anywhere.
errorMid-stream error (e.g. overloaded_error).
Delta types inside content_block_delta
delta.typeMeaning
text_deltaA chunk of visible text — concatenate .text.
input_json_deltaA tool call’s arguments as partial_json — concatenate the string, then parse once.
thinking_deltaExtended / adaptive thinking text — concatenate .thinking.
Where the tokens are Input tokens land once on message_start; output tokens accumulate and are reported on message_delta. There is no single “usage” event — you read both ends of the stream.
