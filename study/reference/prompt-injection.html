Prompt injection & security

Two threat models, layered defenses, and the principles underneath.

Domain 7.1 / 7.2 · Security
Two threat models
Direct / jailbreakIndirect injection
The user is the adversary, trying to break your instructions. The user is trusted, but Claude processes adversarial third-party content — web pages, emails, documents, tool results.

Layered mitigations

  • Harmlessness screens — pre-screen input with a lightweight model (Haiku 4.5) before the main model.
  • Trust boundaries — treat all retrieved / tool content as untrusted; separate it from instructions with distinct fields and XML tags.
  • Input validation — a speed bump, not a wall.
  • Output monitoring — scan responses for signs of leakage / injection success.
  • Computer / browser use — Anthropic runs classifiers that detect injections and make Claude ask for confirmation; injection resistance is also trained in via RL.
No agent is immune On a combined benchmark, Claude Opus 4.5’s single-attempt attack-success rate was ~4.7% (vs. higher for peers) — but it climbs with repeated attempts (~34% at 10, ~63% at 100). Meaningful residual risk remains; layer defenses and assume some attempts succeed. (Third-party figures; indicative.)

Guardrail layering

Prompt-level guard prompts + classifier / LLM-as-judge (Llama Guard, ShieldGemma, PromptGuard, NeMo Guardrails) + deterministic controls. Prompt guardrails alone are insufficient — they share the same computational substrate as the threat.

Secure-by-design & data

  • AAA / CIA — authentication, authorization, confidentiality, privacy, integrity.
  • Least privilege — pre-approve safe tools, deny dangerous ones; egress allowlists limit exfiltration (but even allowlisted endpoints can be abused — combine with output filtering).
  • PII / data leakage — minimize PII in prompts. Structured outputs are HIPAA-eligible, but PHI must not appear in schema definitions (schemas are cached separately).
