stop_reason is NOT an error A 200 response can still carry stop_reason of end_turn, max_tokens, tool_use, stop_sequence, or refusal. These are normal model outcomes to handle, not HTTP failures to retry. Confusing the two is the classic integration-vs-model debugging mistake (Domain 4).

Retry policy (official SDK)

  • Transient failures are retried twice by default (DEFAULT_MAX_RETRIES = 2), with exponential backoff (0.5s × 2n, capped at 8s) plus jitter.
  • The retry-after header is honored when it’s a sane value (≤ 60s); otherwise backoff applies.
  • Retryable: connection errors, 408 / 409 / 429, and 5xx (including 529). Not retryable without changing the request: 400 / 401 / 402 / 403 / 404 / 413 / 422.
  • Read anthropic-ratelimit-* response headers for remaining headroom; use idempotency keys / custom_ids so a retry can’t double-execute.
