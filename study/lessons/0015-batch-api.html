The Batch API

Half price for work that can wait — the classic realtime-vs-batch call.

Domain 5.4 · Cost & Token Management Domain 2.3 · Batch vs realtime

When a workload is large and not time-sensitive — overnight classification, offline evals, dataset labelling — the Message Batches API runs it asynchronously for 50% off. Knowing when to reach for batch instead of firing synchronous calls is a core cost decision (and the guide’s sample Q1).

Your win: submit a small batch of classification requests and read back the batch handle.

Read alongside The caching & batch sheet: 50% off; up to 100k requests / 256 MB; most finish within an hour, expire at 24h; results kept 29 days; one custom_id per request.

Do it

  1. Build one entry per item, each with a custom_id and a full Messages params body: 
    docs = ["refund please", "where is my order", "love this product"]

batch = client.messages.batches.create(requests=[
    {"custom_id": f"doc-{i}",
     "params": {
         "model": "claude-haiku-4-5", "max_tokens": 50,
         "messages": [{"role": "user",
                       "content": f"Classify intent in one word: {d}"}],
     }}
    for i, d in enumerate(docs)
])
print(batch.id, batch.processing_status)
  2. Poll the batch by id until it’s ended, then retrieve results and match each by its custom_id. (Order isn’t guaranteed — the id is how you pair them.)
  3. Notice what you gave up: no streaming, no interactive tool loop. Batch is fire-and-collect.
Realtime vs batch User-facing? Use realtime (sync / streaming). Tolerant of up to 24 hours? Use batch and pay half. Lowering max_tokens or shrinking the model does not address this tradeoff — the axis is latency tolerance, not output size.
