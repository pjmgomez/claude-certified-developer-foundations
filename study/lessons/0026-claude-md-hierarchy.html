The CLAUDE.md hierarchy

How Claude Code assembles its project memory — and why order and size matter.

Domain 3 · Claude Code Operation Domain 2.6 · Configuration

CLAUDE.md is the memory you write for Claude Code — build commands, conventions, gotchas. Several files at different scopes are loaded and concatenated at launch, so knowing the order (and keeping each file small) directly shapes how Claude behaves.

Your win: generate a CLAUDE.md with /init, trim it under 200 lines, and pull in a shared doc with an @import.

Read alongside The Claude Code files sheet: managed → user → project → local, concatenated, not overriding.

Do it

  1. In a real repo, run /init. Claude analyses the codebase and writes a starter CLAUDE.md (build/test commands, conventions). If one exists, it suggests improvements rather than clobbering it.
  2. Trim it toward under 200 lines. A bloated CLAUDE.md burns context every turn and dilutes attention — keep it high-signal.
  3. Factor shared guidance into a separate file and pull it in: 
    # CLAUDE.md
@docs/conventions.md      # imported inline (max depth 4 hops)
  4. Add a subdirectory CLAUDE.md (e.g. packages/api/CLAUDE.md). Confirm it loads on demand when you work in that folder — not at launch like the top-level files.
Concatenated, not overriding Managed, user, project, and local files all add up — a later tier doesn’t replace an earlier one. Put personal, uncommitted notes in CLAUDE.local.md (gitignored); put team-shared rules in the project file.
