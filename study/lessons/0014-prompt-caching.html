Prompt caching

Pay full price for a big prefix once, then a tenth of it on every reuse.

Domain 5.4 · Cost & Token Management Domain 2.3 · Caching

If a large chunk of your prompt is stable across calls — a long system prompt, a tool set, a document — caching lets Claude reuse it instead of re-reading it at full price. A cache read costs ~10% of the base input rate. On repetitive workloads this is the single biggest cost lever.

Your win: cache a large system prompt, then prove the hit by watching cache_read_input_tokens jump on the second call.

Read alongside The caching & batch sheet: read 0.1×, 5-minute write 1.25×, 1-hour write 2× (PROVISIONAL); pays off after one read (5m) or two (1h).

Do it

  1. Put a cache_control breakpoint on a big, stable system prefix: 
    BIG = open("manual.md").read()          # a large, stable prefix

def ask(q):
    return client.messages.create(
        model="claude-sonnet-5", max_tokens=300,
        system=[{"type": "text", "text": BIG,
                 "cache_control": {"type": "ephemeral"}}],   # ttl defaults to 5m
        messages=[{"role": "user", "content": q}],
    )

r1 = ask("Summarize section 2.")
print("write:", r1.usage.cache_creation_input_tokens,
      "read:", r1.usage.cache_read_input_tokens)
  2. Ask again within 5 minutes and compare: 
    r2 = ask("Now summarize section 3.")
print("write:", r2.usage.cache_creation_input_tokens,   # ~0
      "read:", r2.usage.cache_read_input_tokens)        # ~the size of BIG
    The second call reads the prefix from cache — a fraction of the price.
  3. Opt into the 1-hour TTL with {"type": "ephemeral", "ttl": "1h"} when reuse is spread out.
Keep the prefix stable A cache hit needs an identical prefix. Changing tools, tool_choice, or the thinking config near the front invalidates the breakpoint. Put the volatile parts after the cached prefix. max_tokens: 0 pre-warms the cache without generating a reply.
