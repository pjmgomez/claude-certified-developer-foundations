Phase 6 · Claude Application Design

Application design across interfaces

Where an instruction lives changes how well it’s followed.

Domain 2.5 · Claude Application Design 8.6% of the exam

The same instruction behaves differently depending on where you put it — a CLAUDE.md line, a system prompt, a user turn, a tool description. This lesson ties together the placement lessons from the whole course into one design view across Claude Code, Desktop, claude.ai, the API, and the SDKs.

Your win: for a given instruction, pick the right home across interfaces — and know the four design concerns that recur everywhere.

How interfaces layer instructions

SurfaceWhere instructions live
API / SDKssystem prompt (role/scene) + messages (task). You control every layer.
Claude CodeCLAUDE.md + Rules + Skills + settings, then your turns. Persistent project memory.
Claude Desktop / claude.aiApp-managed system prompt + your messages (+ project instructions).

The rule that carries everywhere: system prompt for high-level role and scene-setting; specific task instructions in the user turn, where Claude follows them most closely.

Four concerns that recur

  • Content boundaries. Separate trusted instructions from untrusted data with distinct fields and XML tags (Lessons 0016–0017; hardened in Phase 7).
  • Schema design. Design tool input_schema and structured-output schemas deliberately (Lessons 0008, 0018).
  • Session hygiene. Manage conversation state; clear stale context with /clear and /compact (Lessons 0019–0020).
  • Plugin management. Bundle skills, agents, hooks, and MCP servers as a .claude-plugin/plugin.json for reuse across projects.
Placement is a design decision Don’t bury a must-follow rule in a 300-line CLAUDE.md and hope. Put durable project rules in CLAUDE.md/Rules, role in the system prompt, the specific ask in the user turn, and hard guarantees in tools / structured outputs / hooks — not in prose alone.
