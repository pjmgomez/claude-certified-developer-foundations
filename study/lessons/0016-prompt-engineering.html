Prompt engineering essentials

Clear instructions, examples, XML boundaries, and the right home for each instruction.

Domain 6.2 · Prompt Engineering Domain 6 = 11%

Most “the model got it wrong” problems are really “the prompt was ambiguous.” Four levers do the heavy lifting: be explicit, show examples, mark boundaries with XML, and place each instruction where it belongs.

Your win: take a vague prompt and make it reliable with a role, an example, and XML-tagged data.

The levers

  • Be clear and direct. State the task, the format, and the constraints explicitly — don’t make the model guess.
  • Multishot (few-shot). Show 2–3 worked examples wrapped in <example> tags. Examples beat adjectives.
  • XML tags. Claude was trained on XML structure — wrap inputs and sections in semantic tags (<instructions>, <data>, <example>). This also separates trusted instructions from untrusted data (Phase 7).
  • System vs. user placement. Put high-level role / scene-setting in the system prompt; put the specific task instructions in the user turn, where Claude follows them well.

Do it

  1. Start vague: "Summarize this." — and note the wandering result.
  2. Rebuild it with structure: 
    system = "You are a precise financial analyst. Output exactly three bullet points."

user = """<instructions>
Summarize the report for a busy executive. Lead with the number that moved most.
</instructions>

<example>
- Revenue up 12% QoQ, driven by EMEA.
- Margin flat at 31%.
- Cash runway: 18 months.
</example>

<report>
{PASTE THE REPORT HERE}
</report>"""
  3. Run both and compare. The structured version should be tighter, on-format, and repeatable.
With adaptive thinking, don’t over-prompt Manual “think step by step” chain-of-thought is largely unnecessary when adaptive thinking is on (Phase 3). Reach for the effort dial instead of hand-written reasoning scaffolds.
