Configuration management

settings.json layers, version pinning, and treating prompts like code.

Domain 2.6 · Configuration Management

Shipping Claude reliably means managing configuration the way you manage code: known precedence, pinned versions, and prompts that are versioned and reviewed. Small config drift is a top cause of “it worked yesterday.”

Your win: place a setting at the right layer, and choose a model string you’d actually deploy.

Read alongside The config sheet (settings.json layers + pinning) and Lesson 0011 for the versioning trap.

The levers

  • settings.json layers. Managed policy > user (~/.claude/settings.json) > project (.claude/settings.json) > local (.claude/settings.local.json, gitignored). Put team rules in project; put machine-specific or secret-ish bits in local.
  • Model version pinning. Pin an explicit version in production. Remember the trap: since 4.6, a dateless ID like claude-opus-5 is already a pinned snapshot, not an evergreen pointer — re-test on every upgrade.
  • Prompt versioning. Version prompts alongside code. Changing tool_choice, the thinking config, or budget_tokens invalidates prompt-cache breakpoints — treat a prompt change like a code change (review + test).
  • Plugin dependencies. A plugin (.claude-plugin/plugin.json) bundles skills, agents, hooks, and MCP servers; its manifest declares what it provides so a whole config travels together.
Put the setting in the right place A secret or machine path in the committed project settings.json leaks to the whole team. Local, gitignored settings exist precisely for that — and secrets belong in the environment, not any settings file (Phase 7).
