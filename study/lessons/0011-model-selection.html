Choosing a model

Cheapest tier that clears the bar — and why the version string matters.

Domain 5.3 · Model Selection Domain 5 = 16.8%

There is no “best” model, only the best fit for a task’s quality bar, latency budget, and cost ceiling. The discipline: start cheap, measure against a real eval, and escalate only when the numbers say so.

Your win: a defensible model choice for two different tasks, and a version string you’d actually ship.

Read alongside The models & pricing sheet (all figures PROVISIONAL — verify live): Haiku 4.5 → Sonnet 5 → Opus 5 → Fable 5, cheapest to most capable.

The method

  1. Start at the cheapest plausible tier. Routing, classification, extraction? Begin with Haiku 4.5.
  2. Run an eval on real inputs with clear success criteria. If it clears the bar, stop — you’re done and paying the least.
  3. Escalate one step only if it fails: Haiku → Sonnet → Opus → Fable. Re-measure.
  4. Mixed workloads: route easy cases to Haiku and hard ones to Opus/Sonnet (the routing pattern) rather than paying top rates for everything.
Pin the version In production, use an explicit version, not a convenience alias. And remember the trap: since the 4.6 generation, a dateless ID like claude-opus-5 is already a pinned snapshot, not an evergreen pointer. Re-test on every model upgrade — behaviour can shift.
