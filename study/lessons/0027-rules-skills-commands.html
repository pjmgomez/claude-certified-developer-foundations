Phase 6 · Claude Code

Rules, Skills & Commands

Three ways to extend Claude Code — scoped rules, disclosed skills, and slash commands.

Domain 3 · Claude Code Operation Domain 8.3 · Skills

Beyond CLAUDE.md, three mechanisms shape a Claude Code project: Rules (always-on or path-scoped guidance), Skills (procedural know-how loaded on demand), and Commands (slash-invoked actions). Each has a different loading cost, so each fits a different job.

Your win: author a path-scoped Rule and a Skill, and understand why a Skill costs almost nothing until it fires.

Read alongside The Claude Code files sheet, and the attached writing-for-agents skill for how to word a skill’s description (the trigger).

Do it

  1. Rule — drop markdown in .claude/rules/. Make it path-scoped so it only loads when relevant: 
    # .claude/rules/python-style.md
---
paths: ["**/*.py"]
---
Use type hints on public functions. Prefer pathlib over os.path.
    Unscoped rules load at launch (same priority as .claude/CLAUDE.md); path-scoped ones load only for matching files.
  2. Skill — create .claude/skills/<name>/SKILL.md with YAML frontmatter. Only name + description sit in context (~50–100 tokens); the body loads when the skill is invoked — progressive disclosure: 
    # .claude/skills/release/SKILL.md
---
name: release
description: Cut a release. Use when the user asks to publish or tag a version.
---
1. Run the test suite.
2. Bump the version in pyproject.toml.
3. Tag and push.
  3. Command — note that skills and commands have merged: .claude/commands/release.md and .claude/skills/release/SKILL.md both create /release. Custom commands take $ARGUMENTS.
Why the description is everything A skill’s description is the only part always in context — it’s the trigger. Front-load the leading word and name the branches that should reach it; a must-have skill behind a vague description is a variance bug. (That’s the writing-for-agents lesson.)
