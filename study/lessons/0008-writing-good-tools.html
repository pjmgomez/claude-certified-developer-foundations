Writing tools Claude uses well

The description is the interface. Engineer it like a prompt.

Domain 8.1 · Tool description writing

Whether Claude picks the right tool and fills its arguments correctly depends almost entirely on the description and input_schema — not on cleverness. A vague tool is a coin-flip; a precise one is reliable. Treat tool descriptions with the same care as your prompts.

Your win: turn a sloppy tool into one Claude calls correctly, using description detail and a mistake-proof schema.

The levers

  • Say what it does and when to use it — include purpose, an example, edge cases, and boundaries (“returns at most 50 rows”).
  • Poka-yoke the schema (mistake-proof it): mark required fields, use enum for fixed choices, and prefer unambiguous inputs (absolute paths over relative).
  • Size the tool set — too many tools blurs selection. Keep the set tight; load rarely-used tools on demand (e.g. via tool_search).

Do it

  1. Start sloppy — {"name": "lookup", "description": "look up a thing", "input_schema": {"type":"object","properties":{"q":{"type":"string"}}}} — and watch Claude guess badly.
  2. Rewrite it precisely: 
    {
  "name": "find_order",
  "description": "Look up ONE customer order by its order id. "
                 "Use when the user gives an order number like 'ORD-1234'. "
                 "Returns status and line items. Not for product search.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "e.g. 'ORD-1234'"},
      "include": {"type": "string", "enum": ["status", "items", "all"]}
    },
    "required": ["order_id"]
  }
}
  3. Re-ask an ambiguous question and confirm Claude now calls the right tool with clean arguments.
