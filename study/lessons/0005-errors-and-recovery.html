When calls go wrong

Classify the failure, retry only what’s retryable, and never confuse a stop_reason with an error.

Domain 4 · Debugging & Error Handling Domain 2.3 · API Mechanics

Production code lives or dies on how it handles the unhappy path. Two skills matter: telling a transient failure (back off and retry) from a fatal one (fix the request), and telling an HTTP error from a normal-but-notable stop_reason.

Your win: catch typed exceptions, read status_code and request_id, and wrap a call in correct backoff — honoring retry-after.

Read alongside The HTTP & error taxonomy sheet is your map: retryable = 429 / 500 / 504 / 529 + network; fatal = 400 / 401 / 402 / 403 / 404 / 413.

Do it

  1. Catch specific exceptions, most-specific first: 
    import anthropic

client = anthropic.Anthropic()   # retries transient failures twice by default

try:
    msg = client.messages.create(
        model="claude-sonnet-5", max_tokens=100,
        messages=[{"role": "user", "content": "hi"}],
    )
except anthropic.RateLimitError as e:          # 429
    print("rate limited; retry-after:", e.response.headers.get("retry-after"))
except anthropic.APIStatusError as e:          # any other 4xx / 5xx
    print("status:", e.status_code, "| request id:", e.request_id)
  2. Provoke a fatal error on purpose: use a wrong key (401) or a bogus model name (404/400). Confirm it is NOT retried — retrying can’t fix a bad request.
  3. Add explicit backoff for the retryable set (the SDK already does this; writing it cements the idea): 
    import time, random

RETRYABLE = (anthropic.RateLimitError,        # 429
             anthropic.InternalServerError,   # 500 / 504
             anthropic.OverloadedError,       # 529
             anthropic.APIConnectionError)    # network

def call_with_backoff(make_call, tries=3):
    for attempt in range(tries):
        try:
            return make_call()
        except RETRYABLE:
            if attempt == tries - 1:
                raise
            time.sleep(min(8, 0.5 * 2 ** attempt) + random.uniform(0, 0.5))
  4. Separate model outcomes from failures — this is a 200, not an exception: 
    if msg.stop_reason == "max_tokens":
    print("truncated — raise max_tokens or continue the turn")
429 vs 529 429 rate_limit_error is your account hitting a limit (honor its retry-after). 529 overloaded_error is the API overloaded across everyone. Both are retryable with backoff — but they mean different things when you read logs.
