Domain 1.3 · Agent Patterns

Before you reach for a full agent, most problems yield to one of five composable patterns. The exam expects you to name each and tell them apart — especially orchestrator–workers vs. parallelization.

Your win: implement routing (cheap vs. capable model) and a two-step prompt chain, and articulate what separates the orchestrator pattern from plain parallelization.

The five

  1. Prompt chaining — fixed sequential steps; each processes the last output; add programmatic gates between them. Trades latency for accuracy. (Outline → draft → polish.)
  2. Routing — classify the input, then dispatch to a specialised follow-up. Send easy queries to Haiku, hard ones to Opus. Separation of concerns.
  3. Parallelization — sectioning (split into independent subtasks run at once) or voting (run the same task several times for confidence or diversity).
  4. Orchestrator–workers — a central LLM dynamically decides the subtasks, delegates to workers, and synthesizes. The subtasks are not predefined — that’s the whole difference from parallelization. Great for coding across many files.
  5. Evaluator–optimizer — one LLM generates, another evaluates and returns feedback, looping until it’s good. Needs clear eval criteria.

Do it

  1. Build a router: a cheap Haiku call classifies the request as simple or hard, then your code sends it to Haiku or Opus accordingly. One classifier, two downstream paths.
  2. Build a two-step chain with a gate: step 1 drafts; your code checks a condition (length? contains a required field?); only if it passes does step 2 refine. The gate is plain Python, not a model call.
The classic mix-up Parallelization’s subtasks are fixed in advance; orchestrator–workers discovers them at runtime. If your code already knows the split, it’s parallelization. If the model decides the split, it’s the orchestrator.
