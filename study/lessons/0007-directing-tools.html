Directing tools

Force a tool, allow many at once, and know where each one runs.

Domain 8.1 · Tool Implementation

The loop from the last lesson leaves the decision to Claude. Often you want more control: guarantee a tool runs, pin a specific one, or cap it at a single call. That is tool_choice. And you should know where a tool executes — in your process, or on Anthropic’s.

Your win: force a specific tool for structured output, trigger a parallel call, and name which of your tools are client-side vs server-side.

Read alongside The tool_choice & tool types sheet: auto (default), any (must use one, model picks), tool (force a named one), none.

Do it

  1. Force one specific tool — the trick for reliable structured output: 
    resp = client.messages.create(
    model=MODEL, max_tokens=400, tools=tools,
    tool_choice={"type": "tool", "name": "get_weather"},
    messages=[{"role": "user", "content": "Weather in Paris?"}],
)
# resp.content[0] is a tool_use block for get_weather, guaranteed.
  2. Require some tool but let Claude choose which: tool_choice={"type": "any"}.
  3. Trigger parallel calls: give two cities in one question and watch a single assistant turn contain two tool_use blocks. Return both tool_results in one user turn. To forbid that, add "disable_parallel_tool_use": true.
  4. Label your tools: your get_weather is a client tool (you run it). web_search and code_execution are server tools (Anthropic runs them).
Cache-aware Flipping tool_choice or editing the tools array between calls invalidates cached blocks (Phase 3 covers caching). Keep them stable when you want cache hits.

Check yourself
